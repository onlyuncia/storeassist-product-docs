# Метрики и критерии приёмки

Для основного кейса выделены три показателя: [задержка сообщения «Не найдено»](#m-08), [повторный безрезультатный поиск](#m-09) и [время до передачи](#m-01). Остальные показатели помогают проверить, не скрывают ли успешные выдачи незавершённые запросы, отмены и задержки передачи работы.

Ниже — план измерения и критерии требуемого поведения. Измеренных результатов пилота пока нет.

## Что измерять

### Выдача, поиск и отмена

| ID | Показатель | Определение и граница |
| --- | --- | --- |
| M-01 | <a id="m-01"></a>Время до передачи | Медиана и P90 разницы между созданием принятого системой запроса и сохранённым подтверждением фактической передачи сотрудником склада на терминале; только завершённые передачи |
| M-02 | <a id="m-02"></a>Ожидание принятия | Время от создания до первого принятия в работу; дополнительно — возраст ещё не принятых запросов |
| M-03 | <a id="m-03"></a>Длительность поиска | Время от первого принятия до готовности или исхода «не найдено»; группы считать отдельно |
| M-04 | <a id="m-04"></a>Доля «не найдено» | Число запросов с этим исходом / все запросы одной когорты создания; незавершённые считать отдельно |
| M-05 | <a id="m-05"></a>Доля отмен «покупатель ушёл» | Число финальных отмен с этой причиной / все запросы одной когорты создания. Это отметка продавца, а не доказанная потеря продажи |
| M-06 | <a id="m-06"></a>Незавершённые запросы | Количество и возраст открытых запросов на момент среза, отдельно с ожидающей подтверждения отменой |
| M-07 | <a id="m-07"></a>Работа после запроса отмены | Время от запроса отмены начатой задачи до её фактического разрешения; отдельно случаи подтверждённой передачи |

### Сообщение результата и расхождения

| ID | Показатель | Определение и граница |
| --- | --- | --- |
| M-08 | <a id="m-08"></a>Задержка сообщения «Не найдено» | Медиана и P90 времени от завершения безрезультатного поиска до ознакомления продавца с результатом. В AS-IS — личное сообщение в зале, в TO-BE — результат в iPod; случаи личного сообщения при потере связи учитывать отдельно |
| M-09 | <a id="m-09"></a>Повторный безрезультатный поиск | Среди запросов, созданных за период и имевших предыдущий «Не найдено» по тому же магазину и варианту менее чем за 2 часа до создания нового запроса, доля вновь завершившихся «Не найдено». Открытые, отменённые, уточнённые предупреждения и размер группы показываются отдельно |
| M-10 | <a id="m-10"></a>Длительность проверки расхождения | Медиана и P90 от создания обращения до закрытия с результатом; отдельно по наличию и размещению. Рядом — количество и возраст открытых обращений; добавление эпизода не сбрасывает время создания |

### Передача работы и альтернативы

| ID | Показатель | Определение и граница |
| --- | --- | --- |
| M-11 | <a id="m-11"></a>Ожидание передачи поиска | Время от предложения передачи до принятия новым исполнителем; отдельно отказанные, отозванные и ожидающие предложения. Смена исполнителя не сбрасывает [M-01](#m-01) / [M-03](#m-03); время повторного поиска анализируется отдельно от первой попытки |
| M-12 | <a id="m-12"></a>Выдача согласованной альтернативы | Из исходных запросов «Не найдено», по которым продавец открыл подбор, доля имеющих хотя бы один связанный альтернативный запрос с исходом «Передан». Один исходный запрос учитывается один раз; открытые связанные запросы показываются отдельно. Это выдача, а не доказанная покупка |
| M-13 | <a id="m-13"></a>Ожидание передачи обслуживания | Медиана и P90 от предложения передачи до сохранённого принятия новым продавцом; отдельно отказанные, отозванные и ожидающие предложения с их возрастом. Смена продавца не сбрасывает метрики запросов; по одному обслуживанию предложения считаются отдельно |

### Правила измерения

| Область | Правило |
| --- | --- |
| Когорта и доли | Когорта — запросы, созданные за одинаковый период наблюдения в одном магазине. |
| Когорта и доли | Для долей показываются время среза, размер когорты и число незавершённых запросов. |
| Когорта и доли | Суммарно переданные, ненайденные, отменённые и незавершённые должны покрывать всю когорту без двойного счёта. |
| Граница [M-01](#m-01) | [M-01](#m-01) заканчивается отметкой сотрудника склада о фактической передаче. |
| Граница [M-01](#m-01) | Для сравнения AS-IS и TO-BE используется одинаковая граница измерения; при отсутствии сопоставимых исторических событий нужен базовый замер. |
| Граница [M-01](#m-01) | [M-01](#m-01) не включает время до создания запроса и последующую примерку. |
| Граница [M-01](#m-01) | Его нельзя называть полным временем ожидания покупателя. |
| Граница [M-01](#m-01) | Отменённые и ненайденные запросы не включаются в длительность успешной выдачи; их доли и открытый хвост показываются рядом. |
| Сопоставимость | Нулевая численность даёт «нет данных», а не нулевую долю или длительность. |
| Сопоставимость | Нужны завершённые наблюдения для обеих сравниваемых групп. |
| Сопоставимость | Сравниваются сопоставимые часы, нагрузка и обеспеченность персоналом. |
| Сопоставимость | Стартовый порог визуальной пометки в пилоте — 5 минут от сохранённого времени создания активного запроса. Его можно пересмотреть по результатам наблюдений; целевые значения бизнес-метрик определяются после базового замера. |
| Наблюдение [M-08](#m-08) | Для [M-08](#m-08) нужен замер обеих границ наблюдателем: когда сотрудник закончил поиск и когда продавец ознакомился с результатом. |
| Наблюдение [M-08](#m-08) | Время сохранения исхода и появления уведомления в iPod можно использовать как дополнительные технические показатели, но они не доказывают прочтение продавцом. |
| Наблюдение [M-08](#m-08) | Отдельное подтверждение прочтения в рабочий процесс не добавляется. |
| Данные [M-09](#m-09) / [M-10](#m-10) / [M-12](#m-12) | Для [M-09](#m-09) в обеих сравниваемых группах используется окно менее 2 часов от сохранённого предыдущего исхода до создания нового запроса. Нужны события предыдущих поисков; уточнённые предупреждения показываются отдельно. При изменении окна результаты считаются раздельно. |
| Данные [M-09](#m-09) / [M-10](#m-10) / [M-12](#m-12) | Если исторических событий нет, базу собирают наблюдением. |
| Данные [M-09](#m-09) / [M-10](#m-10) / [M-12](#m-12) | Для [M-12](#m-12) нужны события открытия подбора и связи между запросами; финальный «Не найдено» сам по себе не доказывает уход покупателя. |
| Данные [M-09](#m-09) / [M-10](#m-10) / [M-12](#m-12) | [M-10](#m-10) разбивается по типам проблем, чтобы работа с размещением не скрывалась общей средней. |
| Данные [M-09](#m-09) / [M-10](#m-10) / [M-12](#m-12) | Цели по новым показателям задаются после базового замера. |
| Наблюдение [M-13](#m-13) | Для [M-13](#m-13) нужны идентификатор обслуживания и события предложения / решения с участниками и временем. |
| Наблюдение [M-13](#m-13) | Исторические передачи, если они не фиксировались, требуют базового наблюдения. |
| Наблюдение [M-13](#m-13) | Отсутствие ответа не считается принятием; короткое принятие не доказывает непрерывность обслуживания без проверки общего ожидания и полноты контекста. |

Исход виден в запросе и уведомлении iPod, комментарий — в запросе; выход в зал не требуется, остаток автоматически не исправляется | [FR-08](02-REQUIREMENTS.md#fr-08), [FR-13](02-REQUIREMENTS.md#fr-13) |

| AC-08 | <a id="ac-08"></a>Отмена запрошена после принятия | Запрос остаётся в работе с признаком отмены до ответа исполнителя; затем закрывается по фактическому исходу | [FR-09](02-REQUIREMENTS.md#fr-09), [FR-10](02-REQUIREMENTS.md#fr-10) |
| AC-09 | <a id="ac-09"></a>Ответ на отправку потерян, продавец повторяет попытку | Не возникает дубля исходного действия; показан один установленный результат | [FR-11](02-REQUIREMENTS.md#fr-11), [FR-16](02-REQUIREMENTS.md#fr-16) |
| AC-10 | <a id="ac-10"></a>Активный запрос проверяют в 4 мин 59 с и при достижении 5 мин от сохранённого времени создания; отдельно проверяются «Создан», «В работе» и «Готов к передаче», в том числе с ожидающей отменой | До порога пометки нет; с 5 мин продавец и руководитель видят визуальную пометку с текстом и текущим возрастом запроса. Превышение само не меняет состояние, исполнителя и время создания и не запускает передачу поиска | [FR-14](02-REQUIREMENTS.md#fr-14), [RULE-22](02-REQUIREMENTS.md#rule-22) |
| AC-11 | <a id="ac-11"></a>Найден другой размер | Первоначальный запрос не отмечается переданным; альтернатива требует нового решения продавца | [FR-06](02-REQUIREMENTS.md#fr-06), [FR-07](02-REQUIREMENTS.md#fr-07) |
| AC-12 | <a id="ac-12"></a>Пользователь другого магазина открывает запрос | Данные и действия недоступны | [FR-15](02-REQUIREMENTS.md#fr-15) |
| AC-13 | <a id="ac-13"></a>Продавец читает или не читает уведомление о готовности | Прочтение и отсутствие реакции не меняют состояние; запрос остаётся «Готов к передаче» до подтверждения передачи складом либо другого допустимого перехода | [FR-13](02-REQUIREMENTS.md#fr-13) |
| AC-14 | <a id="ac-14"></a>На складском терминале нет подтверждения сохранения передачи | Интерфейс показывает неопределённый результат до сверки; повтор не создаёт второе событие выдачи | [FR-11](02-REQUIREMENTS.md#fr-11), [FR-16](02-REQUIREMENTS.md#fr-16) |
| AC-15 | <a id="ac-15"></a>Склад открывает очередь своего магазина | Видны актуальные запросы, возраст, состояния и стеллаж / секция из источника либо отметка об отсутствии адреса; ожидающие принятия упорядочены от старых к новым | [FR-03](02-REQUIREMENTS.md#fr-03), [FR-15](02-REQUIREMENTS.md#fr-15) |
| AC-16 | <a id="ac-16"></a>Пользователь открывает историю завершённого запроса | Сохранены участники, времена, переходы, предусмотренные правилами причины и добавленные комментарии; прежние события не заменены последним состоянием | [FR-12](02-REQUIREMENTS.md#fr-12) |
| AC-17 | <a id="ac-17"></a>Обновление остатка перед отправкой не удалось из-за недоступности источника | Показано отсутствие подтверждённых данных; старое значение обозначено отдельно, если доступно. | AC-18 | <a id="ac-18"></a>После готовности обнаружен неправильный размер | Исполнитель возвращает запрос в работу с причиной; история и признак запрошенной отмены сохранены; выдача не подтверждена | [FR-17](02-REQUIREMENTS.md#fr-17) |

## Проверка бизнес-эффекта

1. Собрать базовые наблюдения и проверить полноту фиксации событий.
2. Запустить TO-BE в ограниченной зоне.
3. Сравнить показатели на сопоставимой нагрузке.
4. Проверить общее ожидание и открытые задачи, чтобы ускорение одного этапа не скрыло задержку другого.
